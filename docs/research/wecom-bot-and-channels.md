# 企业微信接入方式与 Claude Code channel 实现要求调研

- 查阅日期：2026-11-12。
- 目的：在动手做 `wecom` 插件之前，确定企业微信用哪种方式接入、能做到什么、有哪些限制，以及它和已完成的 `qq` 插件在设计上哪里不同。
- 分工：A 部分（企业微信平台）由 Orca 里的 Codex 会话"channel调研"按 `.scratch/wecom-channel/research/brief-for-astra.md` 的问题清单调研撰写。0、B、C 部分由 Claude Code 开发会话撰写。
- 核对：开发会话对照[长连接官方文档][ws]原文核对了 A 部分最关键的 14 项事实（连接地址、单连接互踢、心跳、24 小时回复窗口、主动发送前提、频控、流式 10 分钟、附件链接 5 分钟与解密算法、上传限制、Markdown 字节上限、流式不支持的组合、页面更新日期、`from.userid` 的明文与加密规则），并从 npm registry 核对了官方 SDK 的版本、依赖和许可证声明，均与 A 部分一致。A 部分其余内容未逐条复核。
- **本次没有做任何实机测试**：没有登录企业微信账号，没有建立真实连接。所有平台行为都是文档结论，需要实机确认的事项列在 A10。
- 证据等级沿用 QQ 调研的写法：【文档明确】指官方文档、帮助中心、官方仓库或官方 npm 包明确写出；【推断】说明推导依据；【未验证】表示官方未说明、资料矛盾或只有第三方陈述。
- 对照材料：[QQ 插件 spec](../../.scratch/qq-channel/spec.md)、[QQ 调研](qq-bot-and-channels.md)。

## 0. 结论摘要

**推荐方案：智能机器人 → API 模式 → 长连接（WebSocket）。** 本机用 BotID 和长连接专用 Secret 主动连 `wss://openws.work.weixin.qq.com`，收消息、回复、主动发送、上传素材都走这一条连接。不需要公网 IP、域名、回调 URL、可信 IP，也不需要自建应用的 CorpID / CorpSecret / access_token。这条路满足本项目的全部硬约束，其他途径（自建应用回调、URL 模式、微信客服、会话存档、群 webhook）要么需要公网入口或可信 IP，要么只能发不能收，详见 A1。

**它能覆盖 QQ 插件的绝大部分功能**（逐项对照见 A9）：私聊收发文本、Markdown、长文本拆分、图片和文件双向、pairing 和 allowlist、文本形式的权限审批都可行。

**与 QQ 插件相比，有六处会改变设计**（展开见 C2）：

1. **一个机器人只能有一条连接，新连接踢掉旧连接。** QQ 是每条连接各收一份。被踢的一方不能自动重连，否则两个进程会互相挤掉。
2. **入站附件链接只有 5 分钟有效，而且文件是 AES 加密的。** QQ 插件"先只记引用、等 Claude 需要时再下载"的做法在这里会过期，需要改成放行后立即下载解密，或明确告知时限。
3. **回复规则不同且更宽松。** 收到消息后 24 小时内可回复；用户发过消息后可主动发送；两者合计每会话 30 条/分钟、1000 条/小时。QQ 的"60 分钟 4 次被动回复"规则不适用，reply policy 要重写。
4. **长度按 UTF-8 字节算，单条上限 20480 字节。** QQ 插件按 2000 字符拆分，拆分函数要支持按字节计量。
5. **没有查到的能力**：普通文本类型的回复（只有 Markdown）、"正在输入"状态、指定某条消息做引用回复、发送后返回平台消息 ID、编辑已完成的消息、表情回应、历史消息查询。QQ 插件里的 `reply_to`、输入状态和"Markdown 失败后改发纯文本"三项不能照搬。
6. **发送者 ID 的形态取决于机器人创建者**：创建者是企业超级管理员时是明文 userid，否则是加密 userid。allowlist 要按 BotID 分区保存，换机器人后需重新配对。

**企业微信多出来的能力**：流式消息（同一条消息原位更新，最长 10 分钟）、模板卡片和按钮点击事件、入站语音自动转文字。首版建议都不做，理由见 C3。

**适用人群的边界**：机器人只能和本企业成员对话，不能和个人微信用户或外部群对话。个人可以注册企业微信团队来使用，但"全新未认证的个人团队能否拿到长连接入口"还没有实测，是 spike 的第一项。

**SDK**：官方有 `@wecom/aibot-node-sdk`（npm 1.0.7，2026-05-12 发布，声明 MIT，依赖只有 `axios`、`eventemitter3`、`ws`，没有原生模块和安装脚本），满足插件依赖安装的限制。它比现行文档旧五个月，且与文档有两处矛盾（A4.4），Bun 下也未验证。建议 spike 先试 SDK，并像 QQ 插件那样把它放在 gateway 接口后面。

**下一步**：做 P0 实机 spike（A10 的前六项），需要一个能创建智能机器人的企业微信账号。维护者对插件名、首版范围、附件和语音的决定记在 C6。

## A. 企业微信平台

本部分由 Codex 会话调研撰写，原有章节编号 1 到 10 在这里写作 A1 到 A10。

### A0. 平台调研结论摘要

**推荐智能机器人 → API 模式 → 长连接（WebSocket），使用 BotID + 专用 Secret，由本机主动连接 wss://openws.work.weixin.qq.com。** 官方把无固定公网 IP 场景列为适用场景，收消息、普通回复、主动发送和素材上传都可以走同一连接，不需要自建应用的 CorpID/CorpSecret/access_token。【文档明确】[长连接文档][ws]；【推断】这条路径满足本项目网络约束，应作为首选，而不是把传统自建应用改造成主方案。

最重要的五项限制：

1. **每个机器人同时只有一条有效连接。** 新连接完成订阅会踢掉旧连接；两个 Claude Code 会话不能像 QQ 那样复用同一个机器人并各收一份消息。【文档明确】[长连接文档][ws]
2. **机器人面向本企业成员和内部群。** 外部群、客户群、互联群、上下游群不支持；个人可以注册团队，但“未认证个人团队的新账号实际显示长连接入口并成功对话”仍需 spike 验证。【文档明确】[注册说明][registration]、[机器人使用说明][bot-help]；【未验证】未操作真实个人账号。
3. **回复与主动发送有不同前提。** 普通回复可在收到消息回调后 24 小时内进行；主动发送要求用户先在对应会话向机器人发过消息。两者共享每会话 30 条/分钟、1000 条/小时的限制；流式消息从首次发送起最多刷新 10 分钟。【文档明确】[长连接文档][ws]
4. **入站附件链接只有 5 分钟，下载结果仍需解密。** 长连接无需消息信封加解密，不等于附件是明文。直接照搬 QQ 的“只记 URL，等模型需要时再下载”会有链接过期风险。【文档明确】[长连接文档][ws]；【推断】应调整附件生命周期策略。
5. **官方 SDK 可优先评估，但不能把它当成最新平台规则。** npm 最新版是 1.0.7（2026-05-12），晚于 GitHub main 的 1.0.6，却早于当前 2026-10 文档；SDK README 声称支持的流式图文和流式加卡片组合，被现行长连接文档明确排除。Bun 运行、最新字段和错误处理都要做验证。【文档明确】[npm 元数据][npm]、[官方 SDK][sdk]、[长连接文档][ws]；【未验证】Bun 运行结果和矛盾功能。

#### A1.2 长连接发布时间、状态与模式关系

- 2026-03-08 官方更新日志新增智能机器人长连接及长连接主动推送；2026-03-13 增加长连接图片、语音、视频、文件发送；2026-10-12 增加智能助理调用和频道来源相关能力。【文档明确】[更新日志][changelog]
- 长连接文档当前页面“最后更新”为 2026/10/10；更新日志页面更新到 2026/10/29。当前帮助中心公开指导用户创建和使用长连接，文档未标注内测、灰度或即将下线。【文档明确】[长连接][ws]、[更新日志][changelog]、[官方接入指引][bot-connect-help]
- 【推断】它是已经公开提供、官方推荐的产品能力，而非需要申请名单的未公开协议；【未验证】没有找到单独宣告“全量正式商用”的公告，也没有找到下线/废弃公告，不能把“未见灰度字样”写成所有企业必然拥有权限。
- API 模式只能在长连接和接收 URL 之间选一种。切换模式会让原长连接或原回调地址失效，不能把两种接收方式用于同一机器人的并行冗余。【文档明确】[长连接][ws]

#### A1.3 凭据、握手、心跳、重连

1. 在智能机器人配置页开启 API 模式，选择长连接，取得 BotID 与专用 Secret。它不是应用 Secret，也不是 URL 模式的 Token / EncodingAESKey。【文档明确】[长连接][ws]
2. 建立到 wss://openws.work.weixin.qq.com 的 WebSocket，然后发送 aibot_subscribe；body.bot_id 和 body.secret 完成机器人认证，headers.req_id 关联请求与应答。应答 errcode = 0 才代表订阅成功；订阅有频率保护，官方未公布数值。【文档明确】[长连接][ws]
3. 官方建议每 30 秒发送 cmd = ping，带自生成 req_id，接收同 req_id 的应答；长时间无心跳会被断开。具体服务器容忍时长未写。【文档明确】[长连接][ws]；【未验证】超时秒数。
4. 官方要求开发者检测断线并重连，但没有 QQ 那样的 session_id / seq / RESUME 命令、恢复窗口或离线消息补发承诺。【文档明确】[长连接][ws] 列出的握手/心跳命令；【未验证】断网期间消息是否补发、补发顺序与保留时长。
5. 官方 SDK README 提供自动认证、心跳 ACK 检测和指数退避重连；默认重连基准 1 秒，倍增到 30 秒，默认最多 10 次，-1 表示不限次数。这是 SDK 策略，不是服务器协议常量。【文档明确】[官方 SDK README][sdk]
6. 上传会话是单独的恢复例外：重连后，未过期的 upload_id 可继续上传剩余分片。不能由此推导聊天消息也支持会话恢复。【文档明确】[长连接上传说明][ws]；【推断】两类状态应分别处理。

#### A1.4 多连接与多 Claude Code 会话

- 同一个机器人同时只能有一个有效长连接；新连接成功订阅会踢掉旧连接，并给旧连接发送 disconnected_event。不会像 QQ 同 shard 的实测结果那样广播给每个进程。【文档明确】[长连接][ws]
- 官方建议高可用采用主备切换，业务侧避免多连接。【文档明确】[长连接][ws]
- 【推断】被其他会话踢下线时不能立即无条件重连，否则两个本机进程可能互相挤掉。首版应使用“每个会话一个机器人”或明确的单实例占用策略；被踢下线应报告冲突并停止竞争，是否交接由用户决定。
- 【未验证】连接建立成功但尚未订阅时是否影响旧连接、异常关闭码、抢占期间是否有消息丢失。文档把互斥生效点写为完成订阅，不能据此推定所有中间状态。

#### A1.5 帧结构、事件和原始示例

协议是 JSON 帧：cmd 指命令；headers.req_id 标识请求；body 装消息/事件；应答含 errcode、errmsg，部分请求另含 body。被动回复必须透传原回调 req_id。【文档明确】[长连接][ws]

以下是官方“订阅请求”的原始示例；BOTID、SECRET、REQUEST_ID 均为文档占位符，不是真实凭据。【文档明确】[长连接：订阅请求][ws]

~~~json
{
    "cmd": "aibot_subscribe",
    "headers": {
        "req_id": "REQUEST_ID"
    },
    "body": {
        "bot_id": "BOTID",
        "secret": "SECRET"
    }
}
~~~

其余帧要点按字段整理如下，避免把 SDK 的事件名误当成线协议 cmd：

| 类别 | 线协议 | body 中的关键字段 / 处理 |
| --- | --- | --- |
| 消息回调 | aibot_msg_callback | msgid、aibotid、chattype、from.userid、msgtype；群聊另有 chatid |
| 事件回调 | aibot_event_callback | msgtype = event；event.eventtype；事件示例有 create_time |
| 事件类型 | enter_chat | 用户当天首次进入单聊；可回复欢迎语 |
| 事件类型 | template_card_event | 用户操作模板卡片 |
| 事件类型 | feedback_event | 用户对机器人回复反馈 |
| 事件类型 | disconnected_event | 新连接建立导致旧连接被断开 |
| 普通回复 | aibot_respond_msg | 使用原消息 req_id，body 选择 stream、markdown、template_card 或媒体 |
| 欢迎语 / 更新卡片 | aibot_respond_welcome_msg / aibot_respond_update_msg | 仅适用于对应事件，需在 5 秒内响应 |
| 主动发送 | aibot_send_msg | 自生成 req_id；body.chatid、chat_type、msgtype |
| 心跳 | ping | 自生成 req_id，不是用户消息 |
| 素材上传 | aibot_upload_media_init / chunk / finish | upload_id、分片及最终 media_id |

#### A1.6 回调备选的具体要求

| 方式 | URL / 域名 | 验证与加密 | 依据及未明确处 |
| --- | --- | --- | --- |
| 自建应用接收 | http 或 https，官方建议 https；平台必须能访问。官方帮助：未认证企业可填公网 IP 或域名，已认证企业不支持填 IP | GET 验证 echostr，校验签名并解密，1 秒内回明文；消息 XML 加密，5 秒无响应会重试，总共重试 3 次 | 【文档明确】[应用接收][app-receive]、[回调地址填写说明][app-url-help]；【推断】无公网入口不满足 |
| 智能机器人 URL 模式 | 不能是内网 URL；HTTPS 证书不能过期或自签。官方接入 FAQ 对 URL 模式提到企业可信域名和 IP / 与企业主体相同备案主体的域名 | Token 验签，EncodingAESKey 解密 JSON，receiveid 为空字符串；GET 校验 1 秒内回明文；回复也加密 | 【文档明确】[机器人 URL 说明][bot-url-help]、[官方接入 FAQ][bot-connect-help]、[加解密方案][bot-crypto] |

【未验证】现行智能机器人技术“概述”只列 URL、Token、EncodingAESKey，没有完整列出 FAQ 提到的域名/IP校验条件。不同认证主体的 URL 校验规则需后台实测；不能把“可信域名备案规则”扩写成所有回调一律需要备案，也不能把平台回调来源 IP 段、可信域名、应用 API 可信出口 IP 混为一项。[机器人概述][bot-overview]、[应用接收][app-receive]、[官方接入 FAQ][bot-connect-help]

### A2. 准入、创建步骤和对话范围

#### A2.1 个人与未认证企业

- 个人可注册：官方注册帮助明确提供手机端创建和官网“个人组建团队”入口，并说明团队形态支持企业形态账号的各项功能，包括电脑端和管理后台。【文档明确】[企业微信注册][registration]
- 未认证企业当前人数上限为“可使用人数 100、通讯录人数 1000”；超过可使用人数会受到收发消息等限制。帮助还描述缓冲期情形，不能把 1000 个通讯录成员理解为 1000 人均可正常使用，也不应沿用旧文章的 200 人说法。【文档明确】[未认证企业人数限制][unverified-limit]
- 智能机器人创建规则允许超级管理员和有创建权限的成员；当前公开规则未写“必须认证企业才可创建 API 长连接机器人”。【文档明确】[机器人使用说明][bot-help]、[官方接入指引][bot-connect-help]
- 【推断】个人创建的小团队具备尝试长连接接入的官方路径，没有企业执照不应直接判为不可用；【未验证】一个全新未认证个人团队能否立即获得智能机器人及长连接入口、是否有地区/账号风控/版本差异，本次未登录验证。
- 【未验证】没有查到一份覆盖所有 API 的“未认证企业功能白名单”。本文只确认上面的人数规则和已查产品准入，不宣称未认证企业拥有所有外部联系人、微信客服或收费能力。

#### A2.2 当前入口和具体步骤

以下入口均来自现行帮助，实施时需以客户端实际版本为准：

1. 管理员可走“管理后台 → 智能专区 → 智能机器人 → 创建 → 新建机器人”；成员可走“电脑端/手机端 → 工作台 → 智能机器人 → 创建机器人 → 手动创建”。【文档明确】[机器人使用说明][bot-help]、[官方接入指引][bot-connect-help]
2. 切换为 API 模式，选择“使用长连接”；取得生成的 Bot ID 和 Secret。API 模式暂不支持预览与调试，保存后在真实会话使用。【文档明确】[官方接入指引][bot-connect-help]
3. 设置可见/可使用成员范围。API 模式还可选“仅个人使用”或“多人使用”；这些 UI 使用模式与长连接/URL 传输方式是不同维度。【文档明确】[机器人使用说明][bot-help]
4. 检查“管理后台 → 智能专区 → 智能机器人 → 权限管理 → API 模式管理 → 可配置『长连接』方式接入的成员”。无权限时 Bot ID/Secret 不展示；通讯录人数大于 1000 的企业默认该权限为空，小于等于 1000 的企业默认与机器人创建权限范围一致。【文档明确】[官方接入 FAQ][bot-connect-help]、[权限管理说明][bot-permission]
5. 机器人详情“去使用 → 发消息”开始单聊；内部群通过“添加成员 → 智能机器人”加入。【文档明确】[官方接入指引][bot-connect-help]、[机器人使用说明][bot-help]

补充规则：

- 每企业最多 300 个机器人，普通成员最多创建 20 个；创建权限默认全员开放，但管理员可按部门、标签、成员收紧。【文档明确】[机器人使用说明][bot-help]
- 【推断】配置 cc-channels 只需要 BotID/Secret 和会话权限，不需要照抄官方 OpenClaw 教程中额外的文档/MCP/业务 API 授权步骤。
- 现行管理后台入口是“智能专区”，旧教程可能写“安全与管理 → 管理工具”。【文档明确】[现行帮助][bot-help]；【未验证】旧入口在不同版本是否仍并存。

#### A2.3 谁能与机器人对话

- 内部单聊面向可见/可使用范围内企业成员；群聊只支持企业内部群，须 @机器人；互联群、上下游群、外部群、客户群不支持。【文档明确】[机器人使用说明][bot-help]、[官方接入 FAQ][bot-connect-help]
- 【推断】推荐路径不能当作“任意个人微信好友都能添加的聊天机器人”。若产品需要微信用户入口，应另评估微信客服；它的身份、会话状态、资质及发送限制与内部机器人不同。[客服接收][kf-receive]、[客服发送][kf-send]
- 【未验证】传统自建应用通过“微信插件”在个人微信中的可见性/交互入口未纳入本次主方案验证；不能把社区所称“个人微信可用”泛化到智能机器人长连接。

### A3. 会话场景、消息身份与 allowlist

#### A3.1 场景与类型

| 场景 | 回调/类型 | 边界 |
| --- | --- | --- |
| 普通单聊文本 | aibot_msg_callback；chattype = single；msgtype = text | 有 from.userid；普通单聊不返回群聊 chatid |
| 内部群 @文本 | 同 cmd；chattype = group；msgtype = text | 返回 chatid；官方描述是群里 @机器人，不是所有群消息 |
| 图文混排 | msgtype = mixed；mixed.msg_item | 单聊和群 @场景；子项为 text/image |
| 图片、语音、文件、视频 | image / voice / file / video | 普通用户消息仅单聊；语音回调内容已经转文本 |
| 引用消息 | 顶层 quote | 引用的文本/图/混排/语音/文件/视频内容；不是独立的 quote 事件类型 |
| 首次进入单聊 | aibot_event_callback；eventtype = enter_chat | 当天首次进入 |
| 卡片按钮/反馈 | template_card_event / feedback_event | 应按事件身份重新检查发送者权限 |
| 非普通用户来源 | compat_info.source = ai_assistant / channel | 不应直接映射为普通私聊 |

表内协议事实均为【文档明确】[接收消息][bot-receive]、[接收事件][bot-events]、[长连接][ws]；“重新检查权限、不要映射普通私聊”为【推断】，依据是事件可能触发操作且来源语义不同。

#### A3.2 ID 的含义与稳定性

- from.userid 是平台提供的发送者/事件操作者身份。机器人创建者为企业超级管理员时返回明文 userid；其他创建者返回“企业主体下的加密 userid”。【文档明确】[长连接][ws]、[接收消息][bot-receive]
- 官方提供将智能机器人 open_userid 转为自建应用明文 userid 的接口；需要自建应用 access_token，且目标成员在应用可见范围内。【文档明确】[应用与机器人对接][id-conversion]
- 【推断】做本 channel 的 pairing/allowlist 不需要换成明文通讯录 ID：应直接保留平台 from.userid 原值，并用 BotID 给本地授权状态分区；不要大小写归一化，不要用昵称或文本里自报的 ID。
- 【未验证】官方未在机器人文档承诺“同一人跨所有机器人/应用/企业始终同值”，也未描述创建者角色变化、成员退企重建或账号信息变更后的长期稳定性。明文 userid 和加密 userid 不应随意混用；更换机器人/企业后应重新确认授权。
- 单聊主动发送的 body.chatid 填用户 userid；群聊填回调取得的 chatid。chat_type 可设 1（单聊）或 2（群聊）；不填或 0 兼容两种并优先按群聊解释，官方建议明确指定。【文档明确】[长连接][ws]
- 【推断】allowlist 必须按发送者检查。群聊 chatid 只能用于路由，不能代表群内每个人都获授权。单聊会话 ID 可用 from.userid，但通知仍应分别保留 sender_id 与 conversation_id。

#### A3.3 可否冒充、去重、时间戳

- 【推断】正常用户不能靠消息正文更改官方 WSS 帧的 from.userid；它来自已认证连接上的平台消息，应当比昵称、自报 ID、引用内容可靠。这个判断依赖 TLS 正确验证、Bot Secret 未泄露，以及插件不接受来自任意来源的伪造帧。
- msgid 是“本次回调的唯一性标志”，官方要求用它排重，因网络原因可能重复回调。req_id 是请求/回复关联标识，两者不等价。【文档明确】[接收消息][bot-receive]、[长连接][ws]
- 普通文本消息原始示例和字段表没有统一消息发送时间字段；事件示例明确有 create_time。SDK 类型把 create_time 写为可选也不是所有普通消息均有时间戳的保证。【文档明确】[长连接][ws]、[官方 SDK][sdk]
- 【推断】普通消息可记录本地 received_at 作为到达时间，若实际回调有明确时间字段再独立保存；不能把到达时间标成平台发送时间。
- 【未验证】跨断线的 msgid 稳定性、重复事件顺序、离线期间是否补发。去重能防重复执行，不能补救未收到的消息。

### A4. 发消息能力与限制

#### A4.1 被动、主动和 URL 回调模式须分开

| 模式 / 操作 | 接口或命令 | 窗口 / 前提 | 次数与频率 |
| --- | --- | --- | --- |
| 长连接普通回复 | aibot_respond_msg，透传原 req_id | 收到回调后 24 小时内可向该会话回复 | 与主动发送合计每会话 30 条/分钟、1000 条/小时；没有写每条入站消息固定只能回复 N 次 |
| 长连接主动发送 | aibot_send_msg，自生成 req_id，带 chatid | 不依赖某条回调，但用户必须先在会话里给机器人发过消息 | 同上；没有写“先发过消息”状态的有效天数 |
| 长连接流式回复 | aibot_respond_msg + stream.id | 相同 stream.id 更新同一消息；首次发送起 10 分钟内完成；finish = true 后不能再更新 | 刷新帧是否逐次计入 30/1000，文档没有细分 |
| 长连接欢迎语 | aibot_respond_welcome_msg | 收到 enter_chat 后 5 秒内 | 只适用于该事件；事件本身是用户当天首次进入 |
| 长连接更新模板卡片 | aibot_respond_update_msg | 收到 template_card_event 后 5 秒内；task_id 匹配原事件 | 只适用于卡片点击事件 |
| 智能机器人 URL 被动流式 | HTTP 回调回复；平台继续发 stream 刷新回调 | 接收消息页写从用户发消息起最多等待 6 分钟；同一用户与同一机器人最多 3 条消息交互中 | 不应把 URL 模式的 6 分钟/3 并行限制直接套到 WSS |
| 智能机器人 URL “主动回复” | POST 回调给出的 response_url | URL 1 小时有效，仍依赖一次用户消息/卡片交互 | 每个 response_url 只能调用一次；不是 WSS 任意 chatid 主动发送 |

表前五行为【文档明确】[长连接][ws]；第六行为【文档明确】[接收消息][bot-receive]；第七行为【文档明确】[主动回复][bot-response-url]。“未细分”“不能外推”的部分为【未验证】或【推断】。

- 【推断】QQ 的 60 分钟/4 次常量不能复用；企业微信的 reply policy 应按 24 小时 req_id、会话频控、stream 生命周期分别判断。
- 【未验证】长时间断线重连后原 req_id 是否仍在 24 小时内有效、主动发送在用户沉默数日后是否可达、主动会话资格如何失效、平台全机器人级额外配额和相关错误码。
- 【推断】只有明确拒绝的发送才考虑换方式；连接断开导致应答未知时不能断言失败后再发，否则可能重复。该建议来自本仓库 QQ 的投递语义要求，并非企业微信承诺幂等。

#### A4.2 消息格式与长度

| 格式 | 长连接支持范围 | 长度或说明 |
| --- | --- | --- |
| 纯文本 text | 文档明确用于欢迎语；普通回复类型表未列 text | 普通文本内容可作为无格式 Markdown 内容发送，但这不等于存在普通 text 接口 |
| Markdown markdown | 普通回复、主动发送 | UTF-8 最多 20480 字节 |
| 流式 stream | 普通回复 | stream.content 最多 20480 UTF-8 字节；更新提交完整内容，示例先 1 后 123，显示为 123 |
| 模板卡片 template_card | 普通回复、主动、欢迎语；点击事件可更新 | 文本通知、图文展示、按钮交互、投票选择、多项选择；各字段有独立限制 |
| 图片/文件/语音/视频 | 普通回复、主动发送；使用 media_id | 上传限制见 A5 |
| 流式图文 msg_item | **现行长连接页明确暂不支持** | URL 被动回复页和 SDK README 却描述支持；不可直接用于主方案 |
| 流式 + 模板卡片组合 | **现行长连接页明确不支持** | URL 模式有 stream_with_template_card，SDK 也有同类方法，须保留模式差异 |
| news 图文链接 | 未在智能机器人 WSS 类型表找到通用 news 发送 | 可以评估 Markdown 图片/链接或图文展示卡片，但不是通用 news API |

表内肯定/排除项为【文档明确】[长连接][ws]、[被动回复][bot-passive]、[模板卡片][bot-cards]、[SDK README][sdk]；未列出的接口为【未验证】，不是断言平台永远不支持。

- 当前机器人 Markdown 示例包含标题、斜体、粗体、有序/无序列表、嵌套引用、链接、图片链接、分割线、行内代码、代码块和表格。【文档明确】[长连接 Markdown][ws]
- 【未验证】删除线、任务列表、数学公式、HTML、所有嵌套组合和不同客户端的完整渲染一致性；不应按 GitHub Flavored Markdown 全量兼容承诺。
- 【推断】拆长文本按 UTF-8 字节计算，每块不得超 20480 字节；留出格式/标题余量并保持顺序，尽量在段落或代码块边界拆分。QQ 的 2000“字符”只是 QQ 插件自定限制，不能作为企业微信 API 常量。
- 【未验证】普通欢迎语 text 的单独字节上限未在查阅页中给出；不要借用群机器人 text 2048 字节限制。原群机器人 webhook 的 Markdown 4096 字节也与智能机器人 20480 字节不同。[消息推送配置][group-webhook]

#### A4.4 必须保留的文档差异

1. SDK README 提供 replyStream 的 msgItem、replyStreamWithCard，现行 WSS 文档却明确不支持 msg_item、stream+card；URL 被动回复页支持这些。现阶段只承诺 WSS 共同支持的能力，矛盾功能单列实测，不用 SDK 方法存在性作平台证据。【文档明确】[SDK][sdk]、[长连接][ws]、[被动回复][bot-passive]
2. 长连接 aibot_send_msg 的 body.msgtype 字段表只列 markdown/template_card，同页后面的格式说明列出四类媒体；2026-03-13 更新日志和官方 SDK 也明确媒体发送。可以认为媒体支持有官方依据，但具体主动/被动组合仍需 spike 覆盖。【文档明确】[长连接][ws]、[更新日志][changelog]、[SDK][sdk]
3. WSS 流式 10 分钟与 URL 回调轮询 6 分钟属于不同模式；不用第三方“约 6 分钟”的描述覆盖当前 WSS 文档。【文档明确】[长连接][ws]、[接收消息][bot-receive]
4. 机器人帮助中的普通模式“最多 10 轮会话”“知识集附件不能直接回复”不能套到本地 API agent 的历史管理或长连接文件发送。【文档明确】[机器人使用说明][bot-help]；【推断】这类帮助页混合了普通模型模式与 API 模式，技术接口页才是相应 transport 的能力依据。

### A5. 附件与素材

#### A5.1 入站

| 入站类型 | 内容获取方式 | 场景 / 大小 / 有效期 |
| --- | --- | --- |
| image | image.url 下载加密文件；WSS 另给 image.aeskey | 普通消息仅单聊；URL 5 分钟；入站图片总大小上限未明确 |
| file | file.url + file.aeskey | 普通消息仅单聊；官方写仅支持 100M 以内文件回调；URL 5 分钟 |
| video | video.url + video.aeskey | 普通消息仅单聊；官方写仅支持 100M 以内视频回调；URL 5 分钟 |
| voice | voice.content | 平台已转成文本；没有给原始音频下载字段。语音时长/原文件上限未明确 |
| mixed | mixed.msg_item 逐项取 text / image | 单聊及群 @；图片按资源处理。WSS 对 image 结构补 aeskey，嵌套图片实际字段需测试 |
| quote 中媒体 | quote 下相应类型结构 | 不能只检查顶层 msgtype；嵌套下载地址和密钥有效性需测试 |

明确项为【文档明确】[接收消息][bot-receive]、[长连接多媒体解密][ws]；表中未明确的大小/时长/嵌套差异为【未验证】。这里的 100M 是文档原有单位，不擅自解释成精确字节数。

- WSS 每个资源 URL 对应独立 aeskey；URL 模式用配置的 EncodingAESKey。算法均为 AES-256-CBC，PKCS#7 填充至 32 字节倍数，IV 取解码后 AES key 前 16 字节。【文档明确】[长连接][ws]、[接收消息][bot-receive]
- 官方 SDK 的 downloadFile(url, aesKey) 下载并解密，返回 Buffer 和可选 filename。【文档明确】[SDK README][sdk]
- 【未验证】长连接资源链接是否还要求额外 HTTP 请求头、附件 Content-Disposition/原始文件名是否始终返回、断线后能否刷新失效 URL、下载重定向约束、解密失败的具体错误类型。
- 【推断】应在 sender gate 通过之后，明确选择“短期立即缓存附件”或“告知模型必须在 5 分钟内主动下载”。如果继续采用按需下载，必须暴露过期错误并让用户重发；后台不能靠历史查询恢复失效链接。
- 【推断】保留 QQ 的安全文件名、状态目录隔离、大小上限和路径校验；入站支持 100M 不等于插件必须允许 100M。按用户授权的产品上限限制下载，避免 Buffer 全量解密带来不必要内存占用。

#### A5.2 出站上传与发送

长连接上传顺序是 aibot_upload_media_init → aibot_upload_media_chunk × N → aibot_upload_media_finish，得到 media_id 后用普通回复或主动发送的对应媒体类型发送。无需为这条路径换取应用 access_token。【文档明确】[长连接上传说明][ws]

| 素材类型 | 官方总大小限制 | 格式 |
| --- | --- | --- |
| image | 不超过 10MB | PNG、JPG/JPEG、GIF |
| file | 不超过 20MB | 未列通用文件扩展名白名单 |
| voice | 不超过 2MB | AMR |
| video | 不超过 10MB | MP4 |

所有类型至少 5 字节；filename 不超过 256 字节。以上均为【文档明确】[长连接上传说明][ws]。【未验证】WSS 语音最大时长、实际 MB 字节定义、文件安全策略拒绝的扩展名集合。

- 每片 Base64 编码前最多 512KB，总共最多 100 片；upload_id 会话 30 分钟内完成，分片可乱序，同一片重复上传自动忽略。可提交文件 MD5 做合并校验；断线后会话未过期可续传。【文档明确】[长连接][ws]
- 临时素材有效 3 天；单机器人上传频率不超过 30 次/分钟、1000 次/小时。此处对象是机器人，不是消息发送的每会话限流。【文档明确】[长连接][ws]
- 【未验证】上传频控究竟按初始化、完成还是所有分片请求计数；3 天到期后媒体消息本身的客户端可下载性；不同机器人之间 media_id 的可复用范围。
- SDK README 的“100 个 512KB 分片，约 50MB 上限”只描述分片理论容量；平台总大小表仍把普通文件限制为 20MB。SDK 说约 50MB 不能据此放大出站文件限制。【文档明确】[SDK README][sdk]、[长连接][ws]；【推断】应采用类型总大小限制。
- 【推断】QQ spec 中图片/文件最多 5MB 的产品限制在企微平台上可保留，均低于 WSS 对应上限；如之后提高上限，应按 image/file 分开处理，不能统一用分片理论容量。

- 【推断】日志应隐藏 subscribe.body.secret、资源 aeskey、带签名下载 URL、response_url；BotID/用户 ID 也应按最小必要输出。平台回包原文可能包含凭据，不能整帧直接打印。

#### A7.4 如自行实现协议

【推断】若 SDK 与 Bun 或现行字段不兼容，一个小型官方协议实现需要处理：WSS 生命周期、subscribe 鉴权、req_id 与应答关联、30 秒心跳、普通断线退避、被踢下线停机、回调校验和 msgid 去重、被动/主动/流式时窗、频控、上传会话和分片、附件 AES 解密、明确拒绝与结果未知的区分。依据为 [长连接协议][ws]，而不是逆向客户端。

【未验证】没有公开消息恢复协议，因此自行实现也不能补出保证无丢失的 resume。需要把“重连成功”与“断线期间消息完整恢复”分开向用户说明。

## B. Claude Code channel 的实现要求

### B1. 官方文档复核（2026-11-12）

今天重新抓取了 [Channels](https://code.claude.com/docs/en/channels) 和 [Channels reference](https://code.claude.com/docs/en/channels-reference) 全文，与 QQ 调研 B 部分逐节对照：

- 【文档明确】能力声明、通知格式、`meta` 键规则、按发送者鉴权、reply 工具、权限转发的四个字段和裁决正则、开发标志的限制、组织策略、研究预览声明，都与 11-10 的记录一致，没有发现实质变化。
- 【文档明确】MCP SDK 仍须留在 1.x：频道文档仍写着 v2 runtime 上"doesn't register a channel server that negotiates protocol revision 2026-07-28"。
- 【文档明确】上次没有摘录、对企业微信有用的一句："Events queue into the session and are processed in order. If several notifications arrive while Claude is busy, they're delivered together on the next turn and Claude handles them as a group. To process independent event streams concurrently, run separate sessions." 含义：Claude 忙的时候消息会积压到下一轮，积压期间入站附件的 5 分钟链接可能已经过期（见 C2 第 2 条）。
- 【文档明确】多个 channel 可以同时加载（"You can pass several plugins to `--channels`, space-separated"）。`wecom` 和 `qq` 同时启用的实测项记在 `.scratch/multi-channel-session/issues/01-verify-two-channels-in-one-session.md`。

### B2. 官方 telegram 插件的补充阅读

QQ 调研主要参考了 discord 插件。这次补读了本机的官方 telegram 插件（`~/.claude/plugins/marketplaces/claude-plugins-official/external_plugins/telegram/server.ts`，插件版本 0.0.7，下文行号均指该文件），因为 Telegram 和企业微信有两个共同点：同一个机器人只允许一个接收方，以及支持按钮交互。

| 做法 | 位置 | 对企业微信的意义 |
| :- | :- | :- |
| **清理残留进程**：启动时读 `bot.pid`，确认那个 PID 的命令行里确实有 `server.ts` 后才发 SIGTERM，然后写入自己的 PID；退出时只在 PID 文件仍是自己时删除。注释说明原因：上一个会话崩溃后，孤儿进程会一直占着唯一的接收名额。 | 56-78、656-668 | 企业微信同样是单连接。孤儿进程占着连接时，新会话连上会把它踢掉，但如果孤儿自动重连就会反过来踢新会话。需要同样的单实例处理。 |
| **孤儿看门狗**：除了监听 stdin 的 `end` / `close` 和各种信号，每 5 秒检查一次 stdin 是否已销毁。注释记录了用 ppid 判断会误触发，所以改成看 stdin。 | 669-680 | 直接可用。 |
| **冲突时有限重试**：轮询遇到 409（另一个实例在收）时退避重试，8 次后放弃并写明原因；其他网络错误无限退避重试。注释记录了早期只重试 409 导致一次网络抖动后永久收不到消息。 | 1001-1045 | 企业微信要区分两种断线：普通网络断开要重连；收到 `disconnected_event`（被新连接踢掉）不能无条件重连。 |
| **照片在放行后立即下载**：照片消息先过 gate，通过后马上下载到 inbox，把本地路径放进 `meta.image_path`；其他文件只放 `attachment_file_id`，等 Claude 调 `download_attachment`。 | 798-818、968-990 | 官方插件里有"放行后立即下载"的先例。企业微信附件链接 5 分钟过期，可以对所有附件都这样做。 |
| **按钮式权限审批**：权限请求发成带三个按钮的消息（See more / Allow / Deny），回调数据带 `request_id`；点击时再次校验点击者在 `allowFrom` 内；裁决后把原消息改写成结果，按钮消失。只发给私聊，不发群。同时保留文本 `yes <id>` 路径。 | 423-452、738-792 | 企业微信的模板卡片和 `template_card_event` 可以做同样的事，但更新卡片必须在点击后 5 秒内，且要实测。首版用文本路径即可。 |
| **命令只在私聊响应**：`/start`、`/help`、`/status` 在群里静默丢弃，注释列了三个理由（泄露配对码、暴露机器人存在、刷屏）。 | 682-690 | 以后做群聊时沿用。 |
| **输入状态和确认表情**：放行后发 typing，可选给消息加一个表情表示已收到。 | 953-963 | 企业微信两者都没有查到接口。 |
| **可配置的拆分**：`textChunkLimit`（上限 4096）、`chunkMode`（按长度或按换行）、`replyToMode`。 | 107-125、363-385、551-553 | 企业微信按字节拆分，上限 20480 字节。 |

## C. 交叉结论

### C1. 推荐的接入方式

用智能机器人 API 模式的长连接，理由按重要程度：

1. 【文档明确】它是唯一不需要公网入口、也不需要可信 IP 的双向途径（A1.1、A6）。
2. 【文档明确】收、发、上传素材都在同一条连接上，只需要 BotID 和 Secret 两个凭据，配置流程和 QQ 的 AppID + AppSecret 形状相同，`configure` skill 可以沿用。
3. 【文档明确】官方把它列为无固定公网 IP 场景的适用方式，2026-03 发布，文档 2026-10 仍在更新，没有灰度或下线标注（A1.2）。
4. 【文档明确】官方提供 npm SDK，依赖全是 registry 上的纯 JS 包，符合 Claude Code 插件依赖安装的限制（QQ 调研 B7：只支持 registry 包、不跑生命周期脚本）。

不选其他途径的原因见 A1.1 的对照表。特别说明两点：不为"兜底"引入自建应用，因为它需要可信 IP；不做 URL 回调模式，因为需要公网地址。

### C2. 与 QQ 插件的设计差异

下面每条写明 QQ 插件现在怎么做、企业微信为什么不能照搬、建议怎么改。建议都是【推断】，要在 spec 阶段定稿。

1. **连接互斥**
   - QQ：同一个机器人的每条连接都收到一份消息，所以多开会话只会造成重复应答（QQ 调研 D9）。
   - 企业微信：【文档明确】只保留一条有效连接，新连接订阅成功后旧连接收到 `disconnected_event` 并被断开。
   - 建议：被踢下线后停止重连，并在会话里报告"这个机器人在别处被连接了"；普通网络断开才退避重连。启动时参考 telegram 插件清理本机残留进程。README 写明一个机器人对应一个会话，多个会话各用各的机器人（用状态目录环境变量区分）。SDK 默认会自动重连，它在被踢时是否停止要在 spike 里确认。

2. **入站附件的生命周期**
   - QQ：通知里只带附件数量，Claude 需要时再调 `download_attachment` 下载。
   - 企业微信：【文档明确】下载地址 5 分钟有效，文件用每个资源各自的 `aeskey` 做 AES-256-CBC 加密。Claude 正忙时消息会积压到下一轮（B1），到时链接很可能已过期，而且没有历史查询接口可以重新取。
   - 建议：发送者通过 gate 之后立即下载并解密到 inbox，受大小上限约束（QQ 插件是 25 MB），通知里给出本地路径或可下载的标识。未放行的发送者的附件一律不下载。超过上限的不下载并在通知里说明。`aeskey` 和带签名的下载地址不写日志。

3. **reply policy**
   - QQ：被动回复在 60 分钟内最多 4 次（插件按计数管理），之后转主动消息，主动消息有每月额度。
   - 企业微信：【文档明确】被动回复透传原消息的 `req_id`，24 小时内有效；主动发送只要求用户此前在该会话发过消息；两者合计每会话 30 条/分钟、1000 条/小时。
   - 建议：有 24 小时内的 `req_id` 就用被动回复，否则用主动发送。需要一个每会话的发送节流，长文本拆成多条时不能超过 30 条/分钟。"结果未知时不重发"的规则保留。`req_id` 在断线重连后是否仍可用是【未验证】，属于 P1 实测项。

4. **文本长度与格式**
   - QQ：按 2000 字符拆分；Markdown 被拒时改发纯文本。
   - 企业微信：【文档明确】Markdown 单条最多 20480 个 UTF-8 字节；普通回复的类型表里没有纯文本类型。
   - 建议：拆分按字节计量，留出余量。没有纯文本降级路径，Markdown 发送被明确拒绝时直接报告失败。

5. **不能照搬的三项 QQ 功能**
   - `reply_to` 引用回复：【未验证】长连接的发送字段里没有引用目标。首版 `reply` 工具不提供这个参数。
   - 输入状态：【未验证】没有查到接口。首版不做。可以用一条未完成的流式消息表示"处理中"，但那是一条可见消息，是否值得做留到流式一起考虑。
   - 返回平台消息 ID：【文档明确】发送应答里只有 `req_id` 和错误码。`reply` 工具返回"已发送"即可，不返回虚构的消息 ID。
   - 入站引用仍然可用：【文档明确】回调里的 `quote` 带被引用的内容，可以像 QQ 插件一样把它放进正文开头。

6. **发送者身份**
   - QQ：`user_openid`，按机器人不同而不同。
   - 企业微信：【文档明确】`from.userid`，机器人创建者是超级管理员时为明文，否则为加密值。
   - 建议：原样保存，不做大小写归一，allowlist 按 BotID 分区。个人团队里创建者自己就是超级管理员，所以最常见的情况下拿到的是明文 userid；明文 userid 属于可识别个人的信息，日志和文档里不要出现真实值。

7. **`instructions` 要写明的平台限制**
   - 告诉 Claude：不能编辑已发送的消息、不能加表情、不能查历史、不能引用回复；附件已经下载在本地路径。

### C3. 官方插件的功能在企业微信上的取舍

| 官方插件的功能 | 企业微信上的对应 | 首版建议 |
| :- | :- | :- |
| `reply`（文本、附件、分片） | Markdown 消息；图片 10 MB、文件 20 MB 以内先上传再发 | 做。附件上限沿用 QQ 插件的 5 MB，以后可以按类型放宽 |
| `download_attachment` | 5 分钟链接 + AES 解密 | 做，但改成放行后立即下载（C2 第 2 条） |
| `edit_message`（进度更新） | 只有未完成的流式消息可以原位更新，最长 10 分钟，结束后不能再改 | 不做。Claude 的任务经常超过 10 分钟，流式的生命周期和"随时改一条旧消息"不是一回事，需要单独设计 |
| `react` | 没有查到接口 | 不做 |
| `fetch_messages` | 没有查到接口 | 不做 |
| 按钮式权限审批 | 模板卡片 + `template_card_event`，更新卡片有 5 秒窗口 | 首版只做文本 `yes <id>` / `no <id>`，按钮留作后续 |
| 群聊 | 仅企业内部群，需 @机器人 | 首版不做，与 QQ 插件的范围一致，但不要在设计上堵死 |
| 输入状态 | 没有查到接口 | 不做 |

企业微信独有、首版同样不做的：欢迎语事件、用户反馈事件、语音转文字（可以顺手支持，因为回调里直接是文字，留到 spec 决定）、智能助理和频道来源的消息（首版直接丢弃，A1.1）。

### C4. 对抽取 `packages/core` 的含义

QQ spec 约定在第二个平台启动时抽取共享代码。对照 `plugins/qq/src/` 的模块，按这次调研的结论分三类。这是从模块职责和文件名判断的，没有逐行读代码确认，抽取前要再核对。

| 类别 | 模块 | 说明 |
| :- | :- | :- |
| 应当与平台无关 | `access.ts`（allowlist、pairing、文件锁）、`permission.ts`（裁决解析）、`outbound-files.ts`（出站文件检查）、`credentials.ts`（两个凭据字段、0600 文件） | 企业微信的需求相同。allowlist 需要支持按机器人分区 |
| 需要加参数才能共用 | `chunk.ts`（要支持按字节计量和不同上限）、`inbox.ts`（下载后要能插入解密步骤，文件名可能来自响应头） | 先看两个平台的实际调用再定接口 |
| 平台专属，不抽取 | `reply-policy.ts`、`access-token.ts`、`gateway.ts` 的具体事件形状、`sdk-gateway.ts` | 企业微信没有 access token；reply policy 规则完全不同 |

【推断】`channel.ts` 里的入站 gate、权限转发、工具分发大概率可以共用骨架，但它依赖 gateway 接口的形状，而企业微信的 gateway 多出"被踢下线""附件需立即下载""被动回复要带 req_id"三个概念。建议先完成 spike，再决定 gateway 接口怎么改，然后才抽取。

### C5. 建议的下一步

1. **P0 spike**（A10 的前六项），产出放在 `.scratch/wecom-channel/spike/`，对应 QQ 的 ticket 01。它回答四个会改变方案的问题：
   - 未认证的个人团队能不能创建智能机器人并拿到长连接的 BotID 和 Secret。
   - `@wecom/aibot-node-sdk` 1.0.7 在 Bun 下能否连接、收发、干净退出。
   - 同一个机器人第二条连接接入时，SDK 和服务端各自怎么表现。
   - 附件的下载解密和上传发送是否如文档所述。
2. spike 通过后写 `wecom` 的 spec，把 C2 和 C3 的建议定稿。
3. 抽取 `packages/core`，然后按 QQ 的 ticket 顺序实现。

spike 需要维护者提供一个企业微信账号并创建智能机器人，凭据通过环境变量或 `configure` 命令提供，不写进仓库。按之前的约定，实机测试只做文档范围内的验证，不做频控或超长内容的边界探测。

### C6. 维护者的决定（2026-11-12）

1. **插件名是 `wecom`。** 它是企业微信官方现行的英文品牌名，官方 npm 作用域 `@wecom`、官方仓库 `wecom-openclaw-plugin` 和 `wecom-cli` 都用它。命令是 `/wecom:configure`、`/wecom:access`，状态目录是 `~/.claude/channels/wecom/`，包名是 `claude-channel-wecom`。
2. **首版范围与 `qq` 插件一致**：只做私聊，包括文本、Markdown、图片和文件双向、pairing、文本形式的权限审批。群聊、流式消息、卡片按钮留到后续版本。
3. **入站附件在发送者放行后立即下载并解密**，上限 25 MB，与 `qq` 插件相同。超过上限的不下载，并在通知里告诉 Claude。
4. **语音消息按文本投递，并在消息属性里标明是语音转写。** 转写出的文字不用于权限审批。
5. **其余没有单独决定的行为，以官方 discord 插件的做法为准**，平台做不到的地方除外。
